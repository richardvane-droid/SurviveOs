# 项目部署与组织规划

这份文档回答"用 Claude 完成这个项目，结构上该怎么部署"：要不要拆多个 Project、目录/编号怎么定、对话怎么开、每次对话结束前要做什么。所有后续对话开新会话前建议先扫一眼本文档。

## 〇、文档维护方式（2026-09-03 起，新增）

`00-总览/` 这套元文档、以及各模块的正式详细内容，现在的权威来源是本地 git 仓库 `~/Projects/SurviveOs/`（在你 Mac 上），不再是 claude.ai Project 知识库。原因和具体做法见仓库根目录的 README.md，摘要：

- claude.ai 上 SurviveOs 项目里的这些文档保留，作为**每个模块对话开始前的背景快照**，但不再是权威版本，也不建议再指望某个模块对话在结束时通过 `project_write` 自动把改动写回这里——39 个模块分散在不同对话里，各自读到的是同一份文档的某个时间点快照，谁最后调用写入谁的版本就会整体覆盖前面别人的修改，是静默覆盖，不会报错提醒，0601 那次"无法自动写入"就是撞上了这类情况。
- 本地仓库用 git 做版本控制，每次改动是一次 commit，有历史、有 diff，不会互相覆盖；即使两处改动确实冲突，git 也会明确提示冲突而不是悄悄丢数据。
- 新的收尾流程见第六节。

## 一、复杂度推演

- **体量**：7 个区域 × 目前已知约 39 个子模块（会持续增补）× 每个模块 3 个阶段 ≈ 全生命周期上百个独立设计产出。粗算下来，把已知子模块全部推进一轮初版设计，大概需要 40~70 次独立对话（多数模块 1 次对话走完三阶段，少数复杂模块会拆成 2~3 次）。这还不含后续修改、复购比价、以及最费时间的部分——实际动手施工本身（那是月/年级别的体力劳动，不是对话能压缩的）。
- **耦合点（少数会牵扯别的模块，做的时候要留意）**：
  - 0211 全屋中枢/数据可视化屏 — 会汇总其它智能模块的数据接口，建议排在地堡内其他模块有点眉目之后再做
  - 0305 3d 打印 — 与 0201 模拟阳光共用同一台拓竹 P1S，别重复采购
  - 0304 光伏储能 — 如果打算给多个模块供电，选型时要预留其他模块未来的用电量，不能只按当前模块算
  - 智能生态标准（华为智慧生活 + HomeAssistant + ESPHome 双钥匙模式）— 已在方法论里定为默认约定，新模块不用重新讨论这一层要不要做，除非确实想换
- **最大风险不是内容难度，是"记忆碎片化"**：每个新对话都是一个全新会话，彼此看不到对方的聊天记录，唯一共享的记忆就是本 Project 的知识库文档（现改为本地仓库）。所以"对话结束前必须把结论写回去"不是锦上添花，是整套系统能不能长期运转的关键——漏了这一步，那次对话做的工作对后续所有对话来说等于没发生过。
- **Claude 目前不能代你在 claude.ai 上批量新建对话**：开新对话是客户端界面动作，Claude 只能把开场白准备好（见《0005-模块对话启动清单》），由你自己点"+新对话"逐个粘贴打开——这样开出来的对话会正常出现在 SurviveOs 项目的对话列表里。

## 二、要不要拆多个 Project：不拆，全部放在 SurviveOs 一个 Project 里

理由：

- 三阶段方法论、全局约束（80% 自己动手/大陆平台选型）、智能生态标准都是跨模块共享的，拆开会导致每个 Project 都要重新维护一份一样的规则，一改全改不动
- 模块之间有真实耦合（3D 打印机复用、光伏容量规划、全屋中枢数据聚合），拆到不同 Project 后 Claude 没法跨 Project 读取，耦合点会被检测不到
- Project 内用 project_search 做语义检索，39+ 个模块文档的规模完全在合理范围内，不会因为都塞一个 Project 就查不到东西

## 三、编号规则

- **区域编号：两位数字，可扩展**。`00` 固定留给总览/元文档（不是物理区域），`01~07` 是当前 7 个物理区域，未来加新区域从 `08` 继续往下编，不影响已有编号。当前对应：00 总览、01 暖村木屋、02 地堡、03 阁楼间、04 阁楼仓库、05 庭院、06 草地、07 钓台。
- **模块/文档编号：四位数字 = 区域两位 + 该文档在本区域内的两位顺序号**。例如：
  - `00-总览/` 里的元文档：0001 总览与方法论、0002 区域与子模块清单、0003 项目部署与组织规划（本文档）、0004 对外站点与发布规范、0005 模块对话启动清单，以后新增 0006 预算总表、0007 决策记录等，规则和物理区域下的模块完全一样。
  - 暖村木屋（01）第 5 个登记的模块 psk 工作台是 `0105`，第 7 个小吧台是 `0107`。
  - 地堡（02）第 1 个模块模拟阳光是 `0201`。
  - 每个区域内序号上限 99，基本不会不够用。
- 新模块/新文档随时可以追加到对应区域的下一个可用两位序号（比如地堡已经编到 0212，下一个新地堡模块就是 0213；总览已经编到 0005，下一份元文档就是 0006），**不需要整体重排**，也不需要因为想插队而占用别人的号。
- 编号只用于排序、文件命名和跨文档互相引用（比如在"全屋中枢"文档里写"接入 0201/0602 的数据"），**不代表推进优先级**——先做哪个完全由用户自己决定，清单里也不会因为编号靠前就默认优先。

## 四、知识库目录结构

本地仓库和 claude.ai Project 按同一套"区域文件夹 / 编号文件"两层组织，文件名用完整四位编码开头，保证不用打开就知道属于哪个区域第几份文档：

```
00-总览/

  0005-模块对话启动清单.md       每个待开模块的复制粘贴开场白（已建立）
  0006-预算总表.md              可选，累计各模块成本核算，建议做完 3~5 个模块后再建
  0007-决策记录.md              可选，跨模块的重要决策留痕，出现第一条跨模块决策时再建
```

各区域下的具体编号对照见《0002-区域与子模块清单》，那份文档是编号的唯一权威来源，本文档只定规则，不重复维护具体编号列表。

## 五、单个模块文档写什么、重内容放哪

模块索引 `.md` 文件（或文件夹里的 README.md）本身**只做轻量索引 + 关键结论**，模板如下：

```
编号：0105
状态：⬜/🚧/✅
最近更新：日期
方案原理推演：（内联摘要，或指向本模块文件夹内 README/HTML 的说明）
设备电商选型：（内联摘要，或指向本模块文件夹内选型文档的说明）
施工交付物：BOM 清单位置 / 代码位置 / STL 文件位置（相对本仓库的路径）
关键决策记录（哪几个点是用户拍板选的，选了什么）
预算摘要：一次性 ¥ / 年度 ¥
```

重内容分流到最适合的载体：

- **方案原理推演 / 设备电商选型的正文**（有图表、有硬件卡片导航的）→ 优先做成单页 HTML 方案文档，直接放进本仓库该模块的文件夹里（例如 `02-地堡/0201-模拟阳光/index.html`），和你原来压缩包里那 3 个已完成子系统的风格一致；也可以视情况用 Artifact 工具在 claude.ai 上再发布一份可分享的版本（用于对外站点/家人朋友查看），但仓库里的文件才是权威存档。简单模块（比如"盆栽"这种没什么可展开的）不必勉强做单独文件，直接写进索引 `.md` 正文即可。
- **施工阶段的代码/配置文件（ESPHome、HomeAssistant yaml）、3D 打印 STL、BOM 表格**→ 作为实际文件放进本仓库该模块文件夹下的 `code/`、`stl/` 等子目录，和方案文档放在一起、一起进 git 版本历史，不再单独维护一个"施工资产"文件夹。

## 六、对话怎么开、怎么收尾（2026-09-03 更新）

- 打开《0005-模块对话启动清单》，在 SurviveOs 项目里点"+新对话"，把想做的那一行粘贴进去发送——这是目前唯一能让新对话出现在项目对话列表里的方式，Claude 没有能代为批量创建对话的工具。
- **默认一个模块一个对话，三阶段在同一个对话里依次做完**（和历史 3 个已完成子系统的做法一致）。只有模块明显偏大（比如 0211 全屋中枢、0304 光伏储能、0205 生态鱼缸这种涉及安全/生态平衡的）才考虑拆成"方案推演一次对话 + 选型/施工另开一次"。
- **每个模块对话结束前**，产出内容（方案文本、BOM、代码、STL 等）通过对话直接交付给你（作为可下载文件，或直接贴出方案正文），**不再依赖该对话自己调用 project_write 写回 claude.ai 项目文档**——那一步现在改成下面这样做：
  1. 你把这次对话交付的内容，带到「本地维护」环节（下面两种方式选一种）落到 `~/Projects/SurviveOs/` 对应位置，git commit 留痕
  2. 同一次维护顺手更新《0002-区域与子模块清单》（本地文件），状态跨档（⬜→🚧、🚧→✅）时按《0004-对外站点与发布规范》的第五节触发总站/画布更新
  3. 如果希望 claude.ai Project 里的知识库也保持同步（方便下次新开模块对话时读到最新状态），把改动过的 `00-总览/` 文档内容同步贴回 claude.ai 项目（这一步是可选的"发布"动作，不再是必须每次都做的收尾动作）

**两种"本地维护"的做法**：

- **方式 A：在这个云端 Cowork 会话里做**——直接跟这个会话说"帮我把刚才 0203 对话里定的方案写进本地仓库"，我会用 Bash/Read/Write/Edit 工具改本地仓库文件、`git commit`，需要的话再帮你 `git push`。适合你人不在电脑前、或者想省事的时候。
- **方式 B：在你自己 Mac 上用 Claude Code CLI 做**——`cd ~/Projects/SurviveOs`，把某个模块对话产出的内容贴给本地的 Claude Code，让它改文件、`git commit`。适合你已经在电脑前、想要完全在本地闭环、不想经过云端的时候。

两种方式改的是同一个 git 仓库，用哪种取决于你当时在哪、想不想联网，不影响仓库内容本身。

- 建议每完成 5 个左右模块，或者隔一段时间，开一次"维护对话"：检查 `0002-区域与子模块清单.md` 状态是否都同步了、几个耦合点（0211/0304/0305）有没有冲突、预算总表要不要更新、总站内容有没有跟实际状态对齐、以及本地仓库有没有 push 到 GitHub 备份。

## 七、命名建议（方便你在对话列表里找）

对话标题建议用「编号·模块名」或「区域·模块」的格式，例如"0203·控温控湿"或"地堡·控温控湿"；如果某个模块拆成多次对话，后面加阶段后缀，例如"0211·全屋中枢-选型"。这只是建议，不影响功能，你可以按自己习惯改。
